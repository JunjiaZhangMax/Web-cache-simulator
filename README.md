# Shared Web Cache Simulator

## 缓存流程可视化

**在线演示：[Cache Flow — Shared Web Cache Simulator](https://shared-web-cache-flow.focalcarnation4.chatgpt.site)**

网站公开访问，无需登录、安装依赖或下载项目。支持 FIFO、LRU、LFU 切换，以及请求查询、命中、回源、淘汰、写入和返回的逐步播放。

在线版本展示发布时生成的数据快照；修改本地 CSV 或页面后，需要重新生成并部署，线上内容才会更新。

### 本地运行

在项目目录运行（仅需 Python 标准库）：

```powershell
python src/visualize.py
```

用浏览器打开生成的 `cache-flow.html`，可离线查看整个缓存流程：

- 切换 FIFO、LRU、LFU；每种策略均从空缓存开始。
- 自动播放、暂停、前后单步、跳到下一请求，或拖动时间轴。
- 逐步观察查询、命中、回源、每次淘汰、写入和返回。
- 查看缓存容量、条目访问记录，以及已完成请求的累计指标。
- 点击请求轨迹中的任意行，跳到该请求完成时。

可指定输入和运行配置；修改参数或 CSV 后重新生成页面，再刷新浏览器：

```powershell
python src/visualize.py --resources data/resources.csv --requests data/requests_reference.csv --capacity-bytes 102400 --hit-latency-ms 5 --output cache-flow.html
```

页面数据由现有 `request_processor` 的真实运行结果生成；可视化回放使用 `SharedCache` 重建各操作后的缓存状态，不发送网络请求。页面是生成时数据的快照。

验证可视化数据：`python -m unittest discover -s tests -p test_visualize.py`。


这是一个基于请求轨迹（trace-driven）的共享 Web 缓存模拟器，**不是真实的 HTTP 代理**，不需要发送网络请求。

本仓库仅提供文件骨架，缓存逻辑、替换策略、模拟流程、指标计算和测试自行实现。

## 文件用途

- `src/main.py`：程序入口。
- `src/cache.py`：共享缓存的数据结构与基本操作。
- `src/simulator.py`：读取请求轨迹，按顺序驱动模拟。
- `src/metrics.py`：统计缓存命中、未命中等指标。
- `src/policies/fifo.py`：先进先出替换策略。
- `src/policies/lru.py`：最近最少使用替换策略。
- `src/policies/lfu.py`：最不经常使用替换策略。
- `src/policies/custom.py`：小组自行设计的替换策略。
- `tests/test_cache.py`：缓存相关测试。

## 示例数据

`data/sample_requests.csv` 每行表示一次请求，按文件中的顺序处理：

- `timestamp`：模拟时间（秒）。
- `client_id`：发出请求的客户端编号；多个客户端共享同一个缓存。
- `url`：资源标识，仅用于模拟，无需访问。
- `size_bytes`：资源大小（字节）。

示例包含不同客户端对相同资源的重复请求，方便以后检查共享缓存行为。

## 实现计划清单

建议按 **先跑通 FIFO 的完整流程 → 验证结果 → 加 LRU/LFU → 设计自定义策略 → 批量实验** 的顺序实现。下面的复选框用于记录进度，不表示功能已经完成。

作业要求两个输入文件：资源信息与请求轨迹。已导入的 `data/resources.csv` 和 `data/requests_reference.csv` 用于正式实现和验证；`tests/reference/` 保存参考答案。原来的 `sample_requests.csv` 仅为入门示例，缺少源站延迟，不能替代这两个输入文件。

### 1. 确定数据格式和统一规则

- [ ] 查看老师两个 CSV 的实际列名。
- [ ] 明确资源信息：资源 ID、大小（bytes）、源站获取延迟（ms）。
- [ ] 明确请求信息：时间、客户端 ID、资源 ID。
- [ ] 统一容量用 bytes、延迟用 ms；读取请求时间时确认原文件单位。
- [ ] 默认容量设为 `102400` bytes（100 KiB），默认命中延迟设为 `5` ms，并允许配置。
- [ ] 明确共同假设：初始缓存为空、请求顺序处理、资源不变、忽略过期时间、所有请求均为可缓存 GET 请求。

先用普通字典表示资源和请求即可，不必一开始设计复杂的类。请求通过资源 ID 查资源信息。

**完成标准：** 能解释一条请求需要哪些数据，以及数据来自哪个文件。

### 2. 实现输入读取——`src/simulator.py`

- [ ] 读取资源文件，建立“资源 ID → 资源信息”的字典。
- [ ] 读取请求文件，得到按时间顺序处理的请求列表。
- [ ] 将大小、时间、延迟转换成合适的数字类型。
- [ ] 检查未知资源 ID、重复资源 ID、非法大小和延迟。
- [ ] 检查请求顺序；时间相同的请求保留原始文件顺序。

初期用 Python 标准库 `csv` 即可。

**完成标准：** 能读取一个小文件，正确打印每条请求对应的资源大小和源站延迟。

### 3. 实现缓存容器——`src/cache.py`

这一层管理容量和缓存条目，具体淘汰谁交给策略。

- [ ] 保存最大容量 `capacity_bytes`。
- [ ] 保存当前占用 `used_bytes`。
- [ ] 用字典保存已缓存资源。
- [ ] 实现查询、插入和删除操作。
- [ ] 为条目保存插入顺序、最近访问顺序、访问次数，供策略使用。
- [ ] 保证每次操作后，占用量等于所有缓存资源大小之和，且不超过容量。

可以用请求序号表示访问顺序，方便处理同一时间发生的请求。

**完成标准：** 手动插入、查询和删除几个资源后，占用量始终正确。

### 4. 约定策略接口，先实现 FIFO——`src/policies/fifo.py`

建议让策略先只负责从当前缓存条目中选择一个要淘汰的资源 ID，由缓存容器负责实际删除和容量更新。

- [ ] 为所有策略约定相同的调用方式和返回值。
- [ ] FIFO 选择最早进入缓存的资源。
- [ ] 命中不改变 FIFO 的插入顺序。
- [ ] 被淘汰后重新插入的资源获得新的插入顺序。

**完成标准：** 缓存依次放入 A、B，再命中 A；需要淘汰时，FIFO 仍选择 A。

### 5. 跑通逐请求模拟——`src/simulator.py`

按下面顺序处理每个请求：

- [ ] 查询缓存，先确定 hit 或 miss。
- [ ] 命中：使用缓存命中延迟，源站流量为 0，更新访问记录。
- [ ] 未命中：使用该资源的源站延迟，源站流量增加资源大小。
- [ ] 资源大于总容量：跳过缓存，不淘汰已有资源。
- [ ] 资源可以缓存但空间不足：重复选择并淘汰资源，直到空间足够。
- [ ] 插入资源，初始化访问记录。
- [ ] 记录本次结果：客户端、资源、hit/miss、延迟、源站流量、淘汰列表。

一次插入可能需要淘汰多个资源，因此应反复检查空间。未命中延迟直接采用源站延迟，不再加 5 ms。

**完成标准：** 用几条手写请求，能逐条解释命中情况、淘汰行为和最终缓存内容。

### 6. 实现指标统计——`src/metrics.py`

统计模块接收每条请求的结果，累计计数，结束后计算指标。

- [ ] 累计请求数、命中数。
- [ ] 累计请求总字节数、命中字节数。
- [ ] 累计总响应时间、源站总流量。
- [ ] 按客户端分别维护同样的计数。
- [ ] 处理空轨迹，避免除以零。

计算公式：

- 命中率 = 命中请求数 ÷ 总请求数。
- 字节命中率 = 命中字节数 ÷ 请求总字节数。
- 平均响应时间 = 总响应时间 ÷ 总请求数。
- 源站流量 = 所有未命中请求的资源大小之和。

比例显示为百分比时乘以 100%。请求总字节数包含重复请求。缓存占用大小与源站流量是不同的量。

**完成标准：** 手算一个小例子，与程序输出完全一致。全局指标由全局累计值计算，不能直接平均各客户端的比例。

### 7. 写第一批测试——`tests/test_cache.py`

- [ ] 空缓存的第一次请求是 miss。
- [ ] 同一资源再次请求是 hit。
- [ ] 客户端 A 缓存资源后，客户端 B 请求同一资源也能 hit。
- [ ] 大小刚好等于容量的资源能够缓存。
- [ ] 超大资源每次都是 miss，且不改变已有缓存。
- [ ] 一次插入可以淘汰多个资源。
- [ ] 命中不增加缓存占用。
- [ ] 空轨迹不会报除零错误。

手算示例：容量为 10 bytes，资源 A 大小为 6 bytes、源站延迟为 100 ms。两个客户端依次请求 A，应得到一次 miss、一次 hit；命中率和字节命中率均为 50%；源站流量为 6 bytes；平均响应时间为 `(100 + 5) / 2 = 52.5 ms`。

**完成标准：** 上述边界情况与手算结果全部通过，再增加其他策略。

### 8. 增加 LRU、LFU——`src/policies/lru.py`、`src/policies/lfu.py`

- [ ] LRU：淘汰最近访问顺序最早的资源。
- [ ] LFU：淘汰插入以来访问次数最少的资源。
- [ ] LFU 次数相同时，按 LRU 决定。
- [ ] 新插入资源的次数设为 1，包含触发插入的这次请求。
- [ ] 淘汰后重新插入，次数重新开始计算。
- [ ] 为 LFU 的平局规则单独添加测试。

短轨迹示例：缓存只能装两个等大资源，请求顺序为 `A, B, A, C`。插入 C 时，FIFO 应淘汰 A，LRU 和 LFU 应淘汰 B。

**完成标准：** 三种策略使用相同的模拟流程，只改变淘汰选择。

### 9. 完成程序入口，并核对参考输出——`src/main.py`

- [ ] 接收资源文件、请求文件、策略、容量、命中延迟等参数。
- [ ] 连接读取、缓存、策略、模拟和统计模块。
- [ ] 输出总指标和每个客户端的指标。
- [ ] 支持保存逐请求日志和汇总结果。
- [ ] 使用 `data/resources.csv` 和 `data/requests_reference.csv`，以 100 KiB 容量、5 ms 命中延迟运行三种标准策略。
- [ ] 对照 `tests/reference/expected_fifo.csv`、`expected_lru.csv`、`expected_lfu.csv` 检查逐请求结果。
- [ ] 阅读 `tests/reference/reference_trace_answer_key.md`，核对缓存状态、淘汰行为及汇总指标。
- [ ] 每次运行都创建新的空缓存和新的统计对象。

**完成标准：** 一条命令能够完成一次模拟，三个标准策略均通过参考结果验证。

### 10. 设计自定义策略——`src/policies/custom.py`

先明确“更好”指什么，例如降低平均响应时间，再选择策略。一个便于入门的候选思路是按以下分数保留资源：

`分数 = 访问次数 × 源站延迟 ÷ 资源大小`

- [ ] 明确优化目标，决定是否采用这个候选方案。
- [ ] 若采用上述方案，淘汰分数最低的资源，分数相同时按 LRU 决定。
- [ ] 明确访问次数的更新和重置规则。
- [ ] 对零大小资源定义处理方式，避免除零。
- [ ] 在小例子上检查选择是否符合设计。

该候选方案倾向保留访问较多、获取较慢、体积较小的资源，可能改善某些负载的响应时间，也可能牺牲大资源的字节命中率。实际优劣需要实验验证，不要求在每个工作负载上都优于标准策略。

**完成标准：** 能说明策略目标、选择依据，以及预期会表现不好的场景。
